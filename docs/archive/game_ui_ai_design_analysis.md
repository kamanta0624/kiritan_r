# ゲームUI「AIっぽい外観」分析まとめ

作成日：2026-06-27  
対象：kiritan_r UI改善のための設計資料

---

## 1. ゲームUIの構成要素

| レイヤー | 内容 | kiritan_r 対応例 |
|---|---|---|
| HUD（常時表示） | リソース・ターン数・状態値 | TopBar（SP・ミーム・収入・拠点） |
| ナビゲーション | メニュー遷移・タブ・戻る | BottomBar・NavButton |
| パネル／モーダル | 詳細情報・確認ダイアログ | 拠点ポップアップ・キャラ詳細 |
| フィードバック | アニメーション・通知・エラー | 戦闘ログ |
| アイコン／バッジ | 状態表示・ショートカット | 「参戦」「前衛」「近接」Pillバッジ |
| タイポグラフィ | 情報階層の骨格 | Rajdhani（数値）・Noto Sans JP（ラベル） |

## 2. 「AIっぽい」印象の根本原因

### 根本：決定ではなく配置で作られている

> 良いUIは小さな決定の積み重ね——パディング量、セリフ体を一箇所だけ使う判断、標準パレットにない色。AIはコンピテンスに最適化され、クラフトには最適化しない。

AIが生成するUIは**コンポーネントを独立に生成した結果、コンポーネント間の関係が設計されていない**。一画面を俯瞰して「これとこれは同じ文脈か」「この差は意図的か偶然か」を問う工程がない。

## 3. AI生成UIの具体的特徴（事例分析から）

### 3-1. レイヤーの衝突

世界観素材とUIシェルが別の時代・別の設計思想から来ている。  
**例（ffa-edo）**：浮世絵キャラ＋`border-radius:8px`の現代ダークカード。UIの質感をどこに合わせるかの決定が存在しない。

### 3-2. コンポーネント間の語彙不一致

同一画面に異なるアイコン語彙が混在する。  
**例（ffa-edo）**：「？」ボタンが2箇所あって両方デザインが違う。同一機能のコンポーネントが複数あるとき、人間のデザイナーはコンポーネントを共通化する。AIは文脈ごとに別々に生成するため不一致が生まれる。

### 3-3. タイポグラフィに重力がない

数値と単位・ラベルが同サイズ・同ウェイト。視線が止まる場所がない。  
**例（ffa-edo）**：「HP 900」「MP 20」のフォントサイズが同一。既製品ゲームは数値を大きく、単位を小さく・細くして1秒以内に値を読める設計にする。  
**英雄戦姫の反例**：「TURN」小文字ラベル＋「151」極大ピンク数字の差が3倍以上——0.5秒で読める。

### 3-4. border-radiusが一律

全コンポーネントに同じ角丸。世界観由来の形状への問い直しがない。  
**アークナイツの反例**：半透明グレー＋直角ボタン。「軍事・産業・SFディストピア」がボタン形状に反映されている。  
**英雄戦姫の反例**：リソースフレームが「巻物の端」を模した曲線形状——CSSデフォルトではなく世界観から造形している。

### 3-5. インタラクティブ要素と静的要素が区別されていない

タップできるもの・できないものが同じ見た目をしている。affordanceの設計がない。

### 3-6. 背景が「壁紙」として機能している

UIとキャラ・背景が統合されていない。背景は雰囲気を出すための壁紙として機能しているだけで、UIのどの要素とも意味的に接続していない。  
**比較**：プリコネR・ツイステはキャラがUIの「前」にいる——UIとキャラが同じ空間として統合されている。  
**英雄戦姫の反例**：地形（砂漠・海・森・山脈）が色差と描き込みで情報を持ち、シルクロードが実線・海路が点線——マップ自体がUIを兼ねている。

### 3-7. 情報密度の管理不在

良いコンポーネントを大量に置けば画面が成立するわけではない。  
**例（プリコネRホーム）**：コンポーネント単体は丁寧に設計されているが、左上に6種類の情報が競合して視線の止まる場所がない。

### 3-8. リソース表示の形式がリソースの性質と無関係

全リソースを同形式（ラベル＋数値）で並べる。リソースの性質差が表現に出ていない。  
**英雄戦姫の反例**：行動ポイント（上限5個）は丸アイコン個数表示、資金（上限なし）は数値表示——性質に合わせて形式を変えている。

## 4. kiritan_r 固有の問題（コード根拠）

### 4-1. NavButtonのaffordance欠如

```js
// SharedUI.jsx
background: hov ? activeBg : 'rgba(0,0,0,.04)',
border: `1px solid ${hov ? activeColor+'44' : BR}`,
color: hov ? activeColor : TXD,
```

非ホバー時：背景`rgba(0,0,0,.04)`＋ボーダー`rgba(0,0,0,.08)`＋テキスト55%透過。  
BottomBar背景`rgba(255,253,251,.97)`との差が極めて小さく、**ボタンとして認識されない**。  
ホバー依存のaffordanceはタッチデバイスで完全に破綻する。

一方「ターン終了」ボタンのみPKグラデーション＋影付き。同一バー内で「押せるもの」が2種類の見た目を持つ——コンポーネント間の関係が設計されていない。

### 4-2. TopBarの情報優先度なし

ターン・ミーム・収入・アクションポイント・拠点が全て同一の視覚処理（10pxラベル＋15px値）で並列。どれが最優先情報か読み取れない。ロゴが情報と同列にある（役割混在）。

アクションポイントが`4/5`のスラッシュ表記——英雄戦姫の丸アイコン個数表示と比較して視認速度が遅い。上限5個という性質に表現形式が合っていない。

### 4-3. BattleSceneのみトークン外の色が存在

```js
// BattleScene.jsx
const STREAM_SP='#7fff00', STREAM_GEN='#a06bff';
```

`#7fff00`（ネオングリーン）がtokens.jsに存在しない。他全画面で一度も使われない色がBattleSceneのみに直書きされており、画面横断の配色断絶の原因。

### 4-4. STATSゲージが情報を持っていない

攻撃22・防御8・SP459・HP15が全て同一の水平バーゲージで表現されている。数値スケールが全く異なる指標を同形式で並べており、**バーの長さが意味を持たない**。

さらに「SP上限：1,200」「HP上限：15」をバー下に再掲——バーで上限が表現できているはずの情報が重複している。

### 4-5. glassが全面適用

TopBar・BottomBar・カード類がすべて`glass()`（`backdrop-filter:blur(16px)`＋半透明白背景）。TopBar/BottomBarは背景が透けても情報的メリットがない。「なぜここがglassか」の答えがなく、ffa-edoの半透明パネル乱用と同構造の問題。

### 4-6. 英語・日本語の使い分け基準不明

STATSセクション：`STATS` `SKILL` `UPGRADE`（英語）  
ボタンラベル：`SP補充` `SP最大値増加`（日本語）  
同じ「機能名」カテゴリ内で言語が混在。ツイステは「主要機能名＝英語グラフィック素材」「補助説明＝日本語WebFont」と明確に分かれている。

### 4-7. 情報とアクションの混在

鬼畜王ランスの設計：情報パネル（読む）とメニュー（選ぶ）を別レイヤーで出す。  
kiritan_rのポップアップカード：「詳細を見る」と「攻撃する」が同一コンポーネント内に並列——「何が分かる場所」なのか「何をする場所」なのかが混在。

### 4-8. PillバッジのコンポーネントがSemanticsを持たない

```js
// FormationScene.jsx
function Pill({ label, color=PK, filled=false, size='md' }) { ... }
```

「参戦」（状態表示）と「近接」（カテゴリ表示）が同一Pillコンポーネント。意味が異なるのに同形状。色で区別されているが色の体系に凡例がない。

### 4-9. 拠点バッジに所有者情報と種別情報が混在

英雄戦姫の設計：赤い旗マーク（所有者）と建物アイコン（種別・文化圏）が完全に分離した2要素。  
kiritan_rの拠点バッジ：「村」「都市」タグ1つに所有者と種別が混在。さらに自軍ピンク「村」タグと敵軍パープル「+」アイコンで形状まで異なり二重に不一致。

## 5. 参照事例からの学び

| ゲーム | 学べる点 | kiritan_rへの適用 |
|---|---|---|
| アークナイツ | ボタン形状が世界観に根ざす（直角・半透明グレー） | 角丸統一の見直し。VOICEROIDデジタル空間の形状語彙を持つ |

## 6. 脱AI設計ルール（kiritan_r向け）

### ルールA：affordanceを2要素以上で表現する

インタラクティブ要素の状態（通常・ホバー・押下・無効）を色・形状・サイズの最低2要素で表現する。1要素のみ（色だけ・サイズだけ）は不十分。ホバー依存のaffordanceは禁止。

### ルールB：情報とアクションを分離する

「読む場所」と「操作する場所」を同一コンポーネントに混在させない。鬼畜王ランスの構造——情報パネル（静的）とメニュー（インタラクティブ）を別レイヤーで出す——を基本形とする。

### ルールC：ボタン形状を角丸に統一しない

kiritan_rはVOICEROIDデジタル空間というテーマを持つ。「ソフトウェア」「音声データ」「デジタル端末」——これらのテーマから逆算した形状語彙を定義する。全コンポーネントに`borderRadius:99`を使う必然性はない。

### ルールD：ゲージは同一スケールの指標にのみ使う

異なる数値スケールの指標（攻撃22 vs SP1200）を同形式のバーで並べない。バーは「現在値/最大値」の比率表示か、同一スケール内の比較にのみ用いる。上限値をバーと別行に再掲しない。

### ルールE：トークン外の色を禁止する

`tokens.js`に存在しない色の直書き禁止。BattleSceneの`#7fff00`は即時トークン化するか削除する。全画面で同一パレットを使うことが画面横断の統一感の前提条件。

### ルールF：英語／日本語の使い分けを宣言する

以下を決定してドキュメント化する：
- 英語を使う場所：セクションラベル・システム語・技術概念
- 日本語を使う場所：機能名・ボタンラベル・プレイヤーへの表示テキスト
- 混在を許容する場所：なし（原則として混在禁止）

### ルールG：glassは「背景が見える意味がある」場所にのみ使う

TopBar・BottomBarはglassを外す。背景が透けることで情報が増えるコンポーネント（マップ上のポップアップカードなど）にのみ適用する。

### ルールH：リソース表示の形式をリソースの性質から決める

- 上限が少なく個数に意味がある（アクションポイント）→ アイコン個数表示
- 上限なし・大きな数値（ミーム・収入）→ 数値表示
- 割合に意味がある（SP残量）→ バー表示

同形式で全リソースを並べない。英雄戦姫を参照。

### ルールI：拠点バッジの所有者情報と種別情報を分離する

所有者（どの勢力か）と種別（村/都市/砦）は別の視覚要素で表現する。英雄戦姫：旗マーク＝所有者、建物アイコン＝種別。自軍と敵軍で形状を変えない——色のみで区別する。

```
- 色の直書き禁止
- border-radiusは全コンポーネント同値にするな
- glassは「背景が透けることに意味がある」場所のみ

- tokens.js外の色
- 所有者情報と種別情報を同一バッジに混在させる
```

## 付録：AI生成UIの telltale signs チェックリスト

画面レビュー時に以下を確認する：

- [ ] インタラクティブ要素が静的要素と同じ見た目をしていないか
- [ ] 同一機能のコンポーネントが複数あるとき、全て同一デザインか
- [ ] ボタン形状が世界観ではなくCSSデフォルトから来ていないか
- [ ] 全パネルのborder-radiusが同じ値ではないか
- [ ] glassが「雰囲気」のために使われていないか
- [ ] ゲージの並びに同一スケール外の指標が混在していないか
- [ ] tokens.js外の色が直書きされていないか
- [ ] 英語・日本語の使い分けが画面内で一貫しているか
- [ ] 情報パネルとアクションが同一コンポーネントに混在していないか
- [ ] 非ホバー状態でボタンがボタンに見えるか
- [ ] リソースの表示形式がリソースの性質と対応しているか
- [ ] 拠点バッジで所有者情報と種別情報が分離されているか
- [ ] ターン・重要数値がラベルと明確なサイズ差を持っているか
