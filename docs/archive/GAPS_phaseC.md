## A. クラファン挑戦

### A-1. 敵の生成方法 **[BLOCK]**

現行は**1フロア1体の固定データ**。`dungeons.json` の `floors[].enemy`（`name` / `charHp` / `charAttack` / `soldiers` / `soldierAtk` / `soldierDef`）を `App.jsx:43-68` の `buildDungeonEnemy` が単騎に変換している。`factionId: '__dungeon__'` / `isLeader: true` / `attackType: 'melee'` 固定、`battleBonus` 全ゼロ。

**メイン2名＋サブ2名への対称化に対応する手段が無い。** 方式案:

- **A案**: `floors[].enemy` → `floors[].enemies[]`（配列）。フロアごとに最大4体定義。既存5フロアの書き換えが要る
- **B案**: 既存1体をプレイヤー編成人数分**複製**。データ変更ゼロ。同名同性能が並ぶ
- **C案**: テンプレート抽選（`characters.json` の `isTemplate:true` 4体、`BuildingSystem.createMobInstance`）

### A-2. ゴール達成条件 **[BLOCK]**

「6種すべて同一効果・種別はフレーバー」と決めたが、**達成条件も同一でよいか未確定**。全種「最深部到達」なら種別の差はラベルだけになる。

### A-3. ゴール報酬の具体的効果 **[BLOCK]**

「挑戦キャラが強化される」だけで**何がどれだけ上がるか未定**。候補: `maxSoldiers` 加算 / `soldierAtk`・`soldierDef` 加算 / `charAttack`・`charHp` 加算 / 好感度 / 複合。
C-3 プロンプトでは「選んで実装してよい」と書いたが、これは設計放棄。決めること。

### A-4. ダンジョンの数とゴールの割り当て **[BLOCK]**

`dungeons.json` は `dungeon_001`（龍泉洞）**1件のみ**。

- ゴール種別6種 = 6ダンジョンか、1ダンジョンで種別を選ぶのか
- 誰がどのダンジョンに挑戦できるのか（全キャラ共通か、キャラ別か）
- 龍泉洞（岩手の実在鍾乳洞）はクラファン会場として妥当か。世界観上「例のアレの領域」だったが定義変更で宙に浮いている

### A-5. 挑戦の回数制限 **[BLOCK]**

- 1キャラ何回挑戦できるか（1回のみ / 何度でも / クリア済みダンジョンは再挑戦不可）
- 1ターンに何回挑戦できるか
- 行動力（AP）を消費するか。消費するなら何点か

### A-6. 挑戦中のゲーム本体ターンの扱い **[BLOCK]**

挑戦は1ターン内で完結するか、複数ターンにまたがるか。
40ラウンドの累積を1ターンで消化する想定なら、挑戦中に敵勢力の行動（防衛戦の発生）は起きない。またがる場合、**参加キャラが不在の間に防衛戦が起きたらどうなるか**が要設計。

### A-7. 失敗時のキャラ状態 **[RISK]**

`soldiers = 0` は確定。`charHp` と `penaltyTurns` は未定。
既存 `dungeonDefeat(charId)` は `charHp=1` / `soldiers=0` / `penaltyTurns=2` にする。これを流用するか、クラファン失敗は別処理にするか（H-1 と重複）。

### A-8. 複数キャラ挑戦時の報酬増加量 **[RISK]**

## C. 戦闘システム

### C-1. 敵編成対称化の適用範囲 **[BLOCK]**

「メイン1名で挑めば敵はメイン1名」は**クラファンの文脈で出た指示**。通常戦闘（拠点攻撃・防衛）にも適用するかが未確認。
適用する場合、`legionAI.getDefendersWithRule` が返す守備隊が2名しかいないケースで人数を揃えられない（C-2 参照）。

### C-2. 対称化で敵が不足する場合 **[BLOCK]**（C-1 で通常戦闘に適用する場合のみ）

拠点の守備隊が2名、プレイヤーが4名のとき。案: モブで埋める / プレイヤー側を敵の人数に合わせて制限 / 不足のまま非対称を許す。

### C-3. メインが撤退した場合 **[RISK]**

`_mainAlive` は `_isAlive` で判定するが、`retreated` は別フラグ。**メインが撤退してサブだけ残った状態**が発生しうる。撤退＝即戦闘終了（変更禁止仕様）なので実害は無い見込みだが、`_calcPool` のフォールバック撤去後に対象0となる経路として残る。

### C-4. SP上限成長の適用範囲 **[BLOCK]**

「戦闘に参加したキャラ」の範囲が未定。

- 攻撃戦のみか、防衛戦も含むか
- ダンジョン戦闘（クラファン・浅層探索）も含むか。含むならクラファン1回で複数戦闘＝複数回加算になる
- 撤退した場合も加算するか

### C-5. SP上限が伸びたときの現在値 **[RISK]**

`maxSoldiers` のみ増え `soldiers` は据え置きか、同時に増やすか。据え置きなら回復は `recoveryRate`（0.05）依存で、上限が伸びるほど満タンまで遠くなる。

## H. 既存実装との衝突

### H-1. `dungeonDefeat` との重複 **[BLOCK]**

既存 `actions.dungeonDefeat(charId)` は `charHp=1` / `soldiers=0` / `penaltyTurns=2`。
クラファン失敗時の処理（ミーム全額没収）と役割が重なる。統合するか、別 action を立てるか。単騎前提のため複数キャラ対応も要る。

### H-2. 撤退不可との整合 **[BLOCK]**

`battleMode: 'dungeon'` は `allowRetreat = false`（撤退不可）。
**クラファン挑戦を途中で諦めて帰る手段**が現状ない。タイムリミット到達を待つしかない。任意帰還を認めるか。認めるならミームはどうなるか。

### H-3. ラウンド上限の使い分け **[RISK]**

クラファン内の各戦闘は `battleMode: 'dungeon'`（1戦闘のラウンド無制限）でよいか。累積40ラウンドの制限があるため、1戦闘が無制限だと1戦で40消費して即終了する事故が起きうる。1戦闘あたりの上限も別途要るか。
